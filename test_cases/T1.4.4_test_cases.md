# Test Cases for T1.4.4 - Hosting

**Test Case 1:  Resource Scaling and Load Handling**

*   **Title:**  Verify Autoscaling Behavior During Simulated Peak Load - AWS

*   **Description:**  This test case verifies that an application deployed on AWS (using Elastic Beanstalk or similar) correctly scales its compute resources (e.g., EC2 instances) when subjected to a simulated peak load scenario. This confirms the autoscaling configuration is functioning as expected. We are specifically testing resource scaling in the context of increased HTTP request load.

*   **Steps:**

    1.  **Deploy Application:** Deploy a test application (e.g., a simple web application that returns "Hello, World!") to AWS using Elastic Beanstalk, EC2 with auto-scaling group, or similar AWS hosting solution.  Ensure a monitoring tool (e.g., CloudWatch) is configured to track CPU utilization, network I/O, and the number of running instances.
    2.  **Establish Baseline:**  Before load testing, monitor the application's performance metrics (CPU, network, instance count) under minimal load.  Record these baseline values.
    3.  **Simulate Peak Load:**  Using a load testing tool (e.g., JMeter, Locust, Gatling), simulate a rapid increase in the number of concurrent users accessing the application.  Start with a manageable number of users (e.g., 10) and gradually increase until a predefined peak (e.g., 500 concurrent users) is reached.  Monitor the load test tool for errors and response times.  The load should be sustained for a defined duration (e.g., 10 minutes) to allow scaling to occur.
    4.  **Monitor Resource Scaling:** Continuously monitor the AWS CloudWatch metrics during the load test.  Specifically, observe the CPU utilization of the EC2 instances, network I/O, and the number of instances running.
    5.  **Analyze Scaling Behavior:** After the peak load test, analyze the CloudWatch metrics.  Note the time it took for the autoscaling group to launch new instances and how quickly the CPU utilization returned to an acceptable level after the peak.
    6.  **Reduce Load:** Gradually reduce the simulated load and monitor the autoscaling group to observe if instances are terminated (scaled down).
    7.  **Record Results:** Document the maximum number of concurrent users achieved, the maximum CPU utilization reached, the number of instances scaled up to, the time taken to scale up, and the time taken to scale down.

*   **Expected Result:**

    *   The application should successfully handle the simulated peak load without crashing or becoming unresponsive.
    *   AWS autoscaling should trigger the launch of new EC2 instances when CPU utilization exceeds a predefined threshold (e.g., 70%).  The launch of new instances should occur within an acceptable timeframe (e.g., within 5 minutes).
    *   The number of running instances should increase proportionally to the increase in load.
    *   The response time of the application should remain within acceptable limits (e.g., below 2 seconds) even under peak load.
    *   When the load is reduced, the autoscaling group should terminate instances to reduce costs, as configured.
    *   No errors should be observed in the load testing tool during the peak load.

*   **Priority:** High

**Test Case 2:  Database Connectivity and Data Integrity during Failover - Azure**

*   **Title:**  Validate Database Failover and Data Consistency - Azure

*   **Description:**  This test case verifies that an application deployed on Azure and connected to an Azure SQL Database can successfully failover to a secondary database instance in the event of a primary database outage.  It focuses on ensuring data integrity and minimal downtime during the failover process. We are specifically testing database availability and data consistency.

*   **Steps:**

    1.  **Deploy Application & Database:** Deploy a test application to Azure (e.g., Azure App Service) and connect it to an Azure SQL Database with geo-replication enabled (primary and secondary). The application should perform basic CRUD (Create, Read, Update, Delete) operations on a test table in the database.
    2.  **Populate Database:**  Populate the test table with a significant amount of data (e.g., 10,000 records).
    3.  **Continuously Write Data:**  Have the application continuously write new data records to the test table in the primary database.  Record the number of writes performed per second to establish a baseline.
    4.  **Force Failover:**  Simulate a primary database outage by manually triggering a failover to the secondary database instance using the Azure portal or Azure CLI.  Monitor the failover process through the Azure portal.
    5.  **Monitor Application Connectivity:**  During the failover process, monitor the application's ability to connect to the database.  Record the time it takes for the application to reconnect to the secondary database.
    6.  **Verify Data Consistency:** After the failover is complete, verify data consistency between the primary (once it's back online) and secondary databases.  Compare the total number of records, checksums of the data, or specific data values to ensure no data loss or corruption occurred during the failover.
    7.  **Resume Data Writes:** Once the application is connected to the secondary database, resume writing new data records to the test table.
    8.  **Failback (Optional):**  If appropriate for your configuration, perform a failback operation to the original primary database after it has recovered.  Repeat steps 5 and 6 to ensure data consistency during the failback process.

*   **Expected Result:**

    *   The application should successfully failover to the secondary database within an acceptable timeframe (e.g., less than 5 minutes).
    *   The application should automatically reconnect to the secondary database without manual intervention.
    *   No data loss or corruption should occur during the failover process. The data in the secondary database should be identical to the data in the primary database before the failover.
    *   The application should be able to resume writing data to the database after the failover is complete.
    *   If failback is performed, the same data consistency checks should pass successfully.
    *   Errors should be logged appropriately during the failover process but should not prevent successful reconnection.

*   **Priority:** Critical
