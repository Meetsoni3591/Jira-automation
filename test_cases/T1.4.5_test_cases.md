# Test Cases for T1.4.5 - Version Control

Okay, here are two detailed test cases covering Git & GitHub functionalities, designed from the perspective of a Senior QA Engineer.  I've tried to choose test cases that represent core, common workflows.

**Test Case 1:  Cloning a Repository and Verifying Local Commit History**

*   **Title:** Verify Successful Repository Cloning and Local Commit History Integrity

*   **Description:** This test case validates the process of cloning a remote Git repository to a local machine and verifies that the complete commit history is accurately downloaded and accessible locally. This ensures developers can start their work with the latest version of the code base and track its changes.

*   **Steps:**

    1.  **Setup:**  Ensure Git is properly installed and configured on the test machine.  A valid GitHub account with appropriate permissions to access the target repository is required.
    2.  **Obtain Repository URL:** Identify the URL of the target GitHub repository (e.g., `https://github.com/<username>/<repository_name>.git`).
    3.  **Open Terminal/Command Prompt:** Open a terminal or command prompt on the test machine.
    4.  **Navigate to Desired Directory:** Navigate to the directory where the repository should be cloned using the `cd` command. (e.g., `cd /path/to/local/workspace`)
    5.  **Execute Clone Command:** Execute the following command in the terminal, replacing `<repository_url>` with the actual repository URL: `git clone <repository_url>`
    6.  **Verify Cloning Success:** Check the terminal output for any error messages during the cloning process.  A successful clone should indicate the completion of the download process.
    7.  **Navigate into Cloned Directory:** Change directory into the newly created cloned repository directory using the `cd` command (e.g., `cd <repository_name>`).
    8.  **Check Local Commit History:** Execute the command `git log --oneline`.  This will display a concise list of commits in the local repository.
    9.  **Compare Local History to Remote History:**  Log in to GitHub in a web browser and navigate to the same repository.  Visually compare the commit history displayed on GitHub with the output from the `git log --oneline` command. Pay attention to the order, commit messages, and hash of the most recent commits.
    10. **(Optional) Verify file content from specific commit:** Checkout a specific commit (`git checkout <commit-hash>`) and verify that the file content reflects what is stored for that commit. After verifying the file content, return to the main branch (`git checkout <branch-name>`).

*   **Expected Result:**

    1.  The repository should be successfully cloned to the specified local directory without any errors.
    2.  The local repository directory should be created with the name matching the repository name.
    3.  The `git log --oneline` command should display a list of commits.
    4.  The local commit history (as displayed by `git log --oneline`) should exactly match the commit history displayed on the GitHub repository webpage in terms of order, commit messages, and commit hashes.
    5.  Checking out a specific commit should result in correct file content for that commit.

*   **Priority:** High (Critical for development workflow)

**Test Case 2:  Create Branch, Make Commits, Push to Remote Repository, and Create Pull Request**

*   **Title:** Verify Branching, Committing, Pushing, and Pull Request Functionality

*   **Description:** This test case validates the core workflow of creating a new branch, making changes to files, committing the changes locally, pushing the branch to a remote repository, and creating a pull request (PR) to merge the changes into the main branch. It ensures that developers can collaborate effectively using Git and GitHub.

*   **Steps:**

    1.  **Setup:**  Ensure Git is properly installed and configured on the test machine.  A valid GitHub account with appropriate permissions to access the target repository is required. The repository should already be cloned locally (as per Test Case 1).  Make sure you are on the main branch (e.g., `main`, `master`).
    2.  **Create a New Branch:**  Execute the following command in the terminal (within the cloned repository directory), replacing `<new_branch_name>` with a descriptive name for the new branch: `git checkout -b <new_branch_name>`
    3.  **Make Changes to a File:**  Open a text file within the repository (or create a new one) and make a simple change, such as adding a line of text or modifying existing content.  Save the file.
    4.  **Stage the Changes:** Execute the command `git add .` to stage the modified file for commit.
    5.  **Commit the Changes:** Execute the following command to commit the staged changes, replacing `<commit_message>` with a meaningful message describing the changes: `git commit -m "<commit_message>"`
    6.  **Push the Branch to Remote Repository:** Execute the following command to push the new branch to the remote repository: `git push origin <new_branch_name>`  If prompted, provide your GitHub credentials.
    7.  **Verify Branch on GitHub:**  Log in to GitHub in a web browser and navigate to the repository. Verify that the new branch (`<new_branch_name>`) is now listed in the "Branches" section.
    8.  **Create a Pull Request:** On the GitHub repository webpage, locate the banner indicating the newly pushed branch. Click the "Compare & pull request" button.  Alternatively, navigate to the "Pull requests" tab and click the "New pull request" button, selecting the newly created branch as the "compare" branch and the main branch as the "base" branch.
    9.  **Fill Pull Request Details:** Provide a title and a description for the pull request.
    10. **Submit the Pull Request:** Click the "Create pull request" button.
    11. **(Optional) Verify pull request content:** Check the pull request to ensure the commit message and modified files are correct.

*   **Expected Result:**

    1.  A new branch should be successfully created locally with the specified name.
    2.  The changes made to the file should be successfully staged and committed.
    3.  The new branch should be successfully pushed to the remote GitHub repository without errors.
    4.  The new branch should be visible in the "Branches" section of the GitHub repository webpage.
    5.  A pull request should be successfully created with the specified title, description, and associated changes.
    6.  The pull request should display the correct commit message and modified files.

*   **Priority:** High (Critical for development workflow and collaboration)
